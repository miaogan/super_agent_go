> ⚠️ **Go 版本强约束**：全环境统一 **Go 1.26.x**。原因见 [02-技术架构设计.md § 2.1](./02-技术架构设计.md)——
> Sonic 原生加速仅支持到 Go 1.26，且 **Sonic 必须 ≥ v1.15.0**（低版本在 Go 1.26 下会因 `GoMapIterator` 未定义而**编译失败**）。
> **禁止升级到 Go 1.27+**，否则 Sonic 将静默回退到 `encoding/json`，性能退回基线。

> ⚠️ **Milvus 版本与安全**：本项目锁 **3.0.2**（2026-09-18 补丁）。相比 2.6，3.0 **默认 `authorizationEnabled: false` 且默认 root 密码为 `Milvus`**，必须显式加固；同时 **9091 端口严禁对外暴露**（CVE-2026-26190，CVSS 9.8）。Go 客户端须用 `github.com/milvus-io/milvus/client/v3 v3.0.2`，**与 2.6 的 `client/v2` 类型不互通**。详见 [02-技术架构设计.md § 4.8](./02-技术架构设计.md)。

> ⚠️ **Milvus 3.0 回滚边界（升级前必读）**：3.0 的"升级容易、回滚困难"体现在四条独立边界上。本项目通过**保持以下开关为默认关闭状态**来守住回滚能力：
> - `common.storage.useLoonFFI` **保持 `false`** —— 一旦启用并落盘，回滚 2.6 不可逆
> - `dataCoord.targetVecIndexVersion` / `targetScalarIndexVersion` **不手动提升** —— 新索引文件格式旧版本无法读取
> - 不混跑新旧版本；服务端、客户端、proto 在**同一变更窗口**内对齐
>
> **唯一可靠的回滚保障是升级前的备份恢复点**（etcd snapshot + MinIO 全量）。"只换镜像就能回滚"是错误认知。

> ⚠️ **PetSet vs Deployment**：Milvus 与 etcd 是**有状态服务**，K8s 中必须用 **StatefulSet + PVC**，禁止用 Deployment（否则 Pod 重建会丢数据）。

### 3.1 目录结构

> 📌 早期规划把 compose 放在 `deploy/docker/` 子目录，实际落地时按
> 「单仓库多模块、compose 与服务平级」的原则做了扁平化——
> **所有部署文件统一在仓库根目录**，与 6 个服务目录平级。

### 3.4 服务 Dockerfile（单一多阶段定义，参数化）

> ★ 本项目**只有一份 Dockerfile**，通过 `build.args` 参数化服务与JSON 引擎。
> 早期规划里的 `service.Dockerfile` + `gateway.Dockerfile` 两份已废弃。
>
> 原因：两份文件意味着两份构建逻辑，任何修复（如基础镜像版本、
> 安全加固）都要改两遍，迟早漏掉一份。而服务间的差异仅是
> `SERVICE` 与 `HEALTH_PORT` 两个参数 —— 值得用参数换单一来源。

**`Dockerfile`（节选，完整见仓库根目录）**

```dockerfile
FROM golang:1.26-alpine

# ★ 必须显式设 GOPROXY，否则在国内网络构建会「静默挂死」。
#   实测 proxy.golang.org 25s 超时无响应（curl exit 124），
#   构建停在 `go mod download all` 不动且无任何错误输出。
#   留成 ARG 是为了内网私有代理可用 --build-arg GOPROXY=... 覆盖。
ARG GOPROXY=https://goproxy.cn,direct
ENV GOPROXY=${GOPROXY} \
    GOSUMDB=sum.golang.google.cn

# apk 源同理：官方源可达但慢（实测整包 174s），换清华源 0.28s。
ARG APK_REPO=https://mirrors.tuna.tsinghua.edu.cn/alpine

# ★ 只装 git：本项目零 cgo 代码，构建一律 CGO_ENABLED=0，
#   gcc / musl-dev / make 完全用不上。
#   实测装齐那三个包要拉 26 个包（约 700MB），
#   在网络受限环境单这一步就要十几分钟，却对产物毫无贡献。
RUN apk add --no-cache git

# 依赖层缓存：只拷 go.work / 各 go.mod，
# 让「只改业务代码」的构建命中依赖层，不重新拉依赖
COPY go.work go.work.sum ./
COPY pkg/go.mod              ./pkg/
COPY gateway/go.mod          ./gateway/
# ... 其余服务 go.mod

RUN --mount=type=cache,target=/go/pkg/mod go mod download all

COPY . .

ARG SERVICE=gateway
# JSON 引擎开关：留空=标准库；sonic=Sonic JIT（仅 amd64/arm64 有加速）
ARG SONIC_TAGS=""
ARG LDFLAGS="-s -w"
ARG SONIC_VER=""

RUN CGO_ENABLED=0 go build \
      ${SONIC_TAGS:+-tags "$SONIC_TAGS"} \
      -trimpath \
      -ldflags "${SONIC_VER:+-X github.com/aegis/pkg/jsonx.sonicVer=$SONIC_VER }${LDFLAGS}" \
      -o /out/app ./${SERVICE}/cmd

FROM alpine:3.20

# ★ ARG / LABEL 不跨 FROM 传递，必须重新声明。
#   不重新声明的实测后果：
#     SERVICE_NAME=（空值）→ Nacos 注册名退化
#     Labels=null         → 引擎标记形同虚设
ARG SERVICE=gateway
ARG SONIC_TAGS=""
ARG APK_REPO=https://mirrors.tuna.tsinghua.edu.cn/alpine
RUN apk add --no-cache ca-certificates tzdata curl && \
    adduser -D -u 10001 aegis

# LABEL 只能写在最后一个 FROM 之后，写在构建阶段会被丢弃
LABEL aegis.json.engine="${SONIC_TAGS:-encoding/json}" \
      aegis.service="${SERVICE}"

COPY --from=0 /out/app /app/app
ENV SERVICE_NAME=${SERVICE}
USER aegis
STOPSIGNAL SIGTERM
ENTRYPOINT ["/app/app"]
```

**构建参数**

| 参数 | 默认值 | 说明 |
| ---- | ------ | ---- |
| `SERVICE` | `gateway` | 要编译的服务名（决定 `./<SERVICE>/cmd`） |
| `HEALTH_PORT` | `8000` | `EXPOSE` 与 `HEALTHCHECK` 使用的端口 |
| `SONIC_TAGS` | 空（标准库） | 设为 `sonic` 启用 Sonic |
| `SONIC_VER` | 空 | sonic 版本号，写入二进制供运行期自检报告 |
| `GOPROXY` | `https://goproxy.cn,direct` | Go module 代理；传空串可回退 `direct` |
| `APK_REPO` | 清华 alpine 源 | 传空串可回退官方源 |

> ⚠️ **镜像版本必须锁定为 `golang:1.26-alpine`**，禁止使用 `golang:latest`。
>
> ⚠️ **关于 `CGO_ENABLED=0`**：Sonic 的 native 实现依赖汇编（amd64/arm64），
> 不依赖 cgo，因此 `CGO_ENABLED=0` 下 Sonic 原生加速**依然可用**，
> 同时可产出静态二进制、缩小镜像体积。
>
> ⚠️ **`-ldflags` 的写法陷阱**：不能写成
> `${SONIC_VER:+-ldflags "-X ... -s -w"}` —— 当 `SONIC_VER` 为空时
> 整个 `-ldflags` 会消失，镜像退化成未剥离符号的二进制（体积多几 MB）。
> 故 `SONIC_VER` 与 `LDFLAGS` 必须分开处理。
>
> ⚠️ **构建挂死时先查网络，再查缓存**。`go mod download` 步骤无输出地卡住，
> 九成是 `proxy.golang.org` 不可达，**不是** Docker 缓存问题 ——
> 此时反复 `--no-cache` 只是浪费时间。验证方法：
>
> ```bash
> docker run --rm golang:1.26-alpine sh -c 'time go list -m all'
> ```

### 3.4.1 `.dockerignore`：构建上下文瘦身

Docker 每次构建都会把整个上下文打包发给 daemon。**未排除时实测 184MB**，
其中绝大部分与构建无关：

| 路径 | 体积 | 说明 |
|------|------|------|
| `.run/` | 124MB | `scripts/dev.sh` 生成的 6 个服务二进制 |
| `tools/` | 27MB | 含误编到根目录的 `smokeclient` 二进制 |
| `docs/`、`*.md` | ~400KB | 不参与构建 |

**必须排除的两类**：

1. **性能** —— 每次构建白传 180MB+；CI 上是纯粹的等待与带宽浪费
2. **安全** —— `configs/*.local.yaml` 可能含真实密钥，
   而镜像层可被 `docker history` 直接看到

> ★ `.run/` 之所以能到 124MB，是因为 `dev.sh` 把 6 个服务的二进制都放在那里。
>   若 `.dockerignore` 漏配，等于把编译好的服务再塞进镜像的构建层 ——
>   既臃肿，又存在旧二进制与新代码不一致的隐患。

**两个必须知道的语法陷阱**：

1. **不支持行内注释**。`.run/  # 产物` 会被当作「匹配 `.run/` 与 `# 产物` 的路径」，
   规则**完全失效且不报错**，表现为「配了但上下文没变小」。
   所有注释必须独占一行。
2. **匹配不区分「同名文件」与「同名目录」**。为排除 smokeclient 二进制而写
   `smokeclient` 或 `**/smokeclient`，会把 `tools/smokeclient/` **整个目录**排掉，
   于是依赖层直接失败：

   ```console
   failed to calculate checksum of ref ...: "/tools/smokeclient/go.mod": not found
   ```

   这个报错**完全不提 `.dockerignore`**，极易误判为 Docker 缓存问题并反复
   `--no-cache` 空转（本项目实际空转 3 轮）。正确写法是精确到文件：
   `tools/smokeclient/smokeclient`。

> **排查手法**：怀疑 `.dockerignore` 时别猜，直接把上下文 dump 出来看真相：
>
> ```dockerfile
> FROM alpine
> COPY . /ctx
> RUN find /ctx -type f | sort && find /ctx -type f | wc -l
> ```
>
> 实测输出 141 文件 / 1.18MB，规则是否生效一目了然。

#### 4.10.1 Milvus 升级与回滚流程（3.0.x）

| 步骤 | 操作 | 说明 |
|---|---|---|
| **1. 备份**（不可跳过） | `etcdctl snapshot save` + `mc mirror` 全量 MinIO | **这是回滚的唯一可靠保障** |
| **2. 确认基线** | 记录当前版本、`useLoonFFI`、`targetVecIndexVersion`、`targetScalarIndexVersion` | 用于升级后对比 |
| **3. 非生产验证** | 在 staging 用同一份备份恢复，改镜像 tag 跑通 | 验证 schema 创建 / upsert / search / delete 全链路 |
| **4. 镜像升级** | 改 `milvusdb/milvus:v3.0.2`，保留 etcd / MinIO / Woodpecker 与数据目录 | 官方确认 Docker Compose 路径只需改 tag |
| **5. 逐版本补丁** | 若从 2.6.18 及更早升，先升到 2.6.19+ 吸收 CUDA 基镜像变更 | CUDA 11.8→12.9.1 发生在 2.6.19，非 3.0 引入 |
| **6. 观察** | 查 compaction、索引重建、写入延迟 | 迁移靠 compaction 渐进完成，非瞬时 |
| **7. 验收** | rag_service 检索链路 + `degraded` 标志正常 | 见 §7.5 |

**升级路径约束（官方）**：

- 受支持路径：`2.6.20+ → 3.0.0`（Operator 1.3.0）
- **不允许切换 MQ 类型**（如 RocksMQ ↔ Woodpecker）
- **不允许从 rc 版本直升**
- Kubernetes 上需先升级 **Milvus Operator 到 1.3.0+**

**回滚边界（务必理解）**：

```
相对可回退的动作                        一旦发生只能前滚或备份恢复
─────────────────────────            ──────────────────────────────
只换了镜像，未产生新写入                 已产生 Storage V3 写入
staging 上验证配置                       compaction 已把存量段重写为 V3
集群尚未生成新索引文件                    已生成旧版本无法读取的新索引
                                           WAL 含旧版本未验证的新语义
```

> 📌 **本项目的回滚保障**：由于我们**保持 `useLoonFFI=false` 且不提升索引版本**，回滚窗口是敞开的。一旦决定启用 Storage V3 或提升索引版本（例如为了 Snapshot / TEXT 字段），**必须在此动作前新建一个备份恢复点**，并把"停止写入"纳入失败处理流程。

```bash
# 升级前备份（示例）
kubectl -n aegis-infra exec etcd-0 -- \
  etcdctl --endpoints=localhost:2379 snapshot save /backup/etcd-$(date +%F).db
mc mirror --overwrite minio/aegis-milvus /backup/minio/aegis-milvus

# 记录基线配置
kubectl -n aegis-infra exec milvus-0 -- \
  curl -s localhost:9091/healthz && \
  grep -E "useLoonFFI|targetVecIndexVersion|targetScalarIndexVersion" /milvus/configs/milvus.yaml
```

## 7. 故障排查手册

### 7.0 向量库（Milvus）——「不报错但结果不对」类问题

>这一类最耗人：**系统不报错、日志干净、指标正常，但检索结果就是不对**。
> 下面的每一条都在真实 Milvus 3.0.2 上实测复现过，不是推测。

| 症状 | 真实原因 | 处理 |
|---|---|---|
| 检索恒定返回 0 条，**且无任何报错** | 默认一致性等级 `ClBounded`，新写入数据落盘前对检索不可见 | 已修复：入库流水线在**整篇文档写完后 Flush 一次**（`vectordb.Syncer`，约 1.2s）。若仍复现，跑 `make milvus-diag` |
| `Unauthenticated: missing authorization in header` | 服务端开了 `authorizationEnabled` 但未提供凭据 | 补 `.env` 的 `MILVUS_USERNAME` / `MILVUS_PASSWORD`。⚠️ 这个错长得像「连不上」，极易误判为 Milvus 未启动 |
| `context deadline exceeded`（连 127.0.0.1 也报） | 地址配的是容器内主机名（如 `milvus:19530`），宿主机 DNS 解析不了 | 探测脚本会自动改写为 `127.0.0.1`；容器内运行则用服务名 |
| `collection not loaded` | 新建集合默认 NotLoad，**检索走 query node，必须先 load** | 适配层已自动 `LoadCollection` + `Await`。该错误信息里没有任何「请先 load」的提示 |
| `database not found[database=aegis]` | SDK 在 `New()` 内部就校验数据库存在 | 必须**两阶段连接**：先连默认库 → `CreateDatabase` → `UseDatabase`。把 `DBName` 塞进 `ClientConfig` 会让建库代码没机会执行 |
| `dim mismatch` / 维度不符 | embedding 模型换了或配置漂了 | 换模型必须全量重新向量化。适配层选择**报错而非补零/截断** |
| `Stats` 显示 `entities=0` | `row_count` 来自已落盘 segment，需等 flush/compaction | **正常现象**，不是写入失败。判断写入成功应看 Search 能否召回 |
| `no matching versions`（go get） | 文档写的 `client/v3 v3.0.2` **不存在**，那是服务端版本号 | 用 `v3.0.0`。客户端与服务端是两条独立版本线 |

**两个能真正帮你定位问题的工具**：

```bash
make milvus-probe   # 11 步真实链路探测：建集合→写入→同步→检索→阈值→查回→删除
make milvus-diag    # 一致性行为实验：写后多久可检索 / Sync 的确切代价
make milvus-clean   # 清理上面两个命令留下的临时集合（白名单，不碰业务集合）
```

>💡 排查检索问题时，**先跑 `milvus-probe`**。
> 它在探测前会用专属 `kb_id` 清空集合，确保断言的每一条结果都只能来自本次写入 ——
> 否则「召回的到底是新数据还是上次的残留」根本分不出来，
> 表现出来就是"第一次跑通过、第二次跑检索为空"，看着像偶发 bug。

> ⚠️ 探测/诊断**故意不删集合**（避免误删业务集合），
> 所以会留下 `aegis_probe_*` / `aegis_diag_*` 残留。定期用 `make milvus-clean` 收拾 ——
> 它走**白名单**（只删这两个前缀），新增命名规则时最坏只是不删，不会误伤。

```bash
make live-check
```

### 7.4.1 检索结果排序不符合预期

**先分清是没重排，还是重排没起作用** —— 看响应的 `degrade_reason`：

```bash
# Debug 检索会返回各阶段明细
curl -s -X POST http://localhost:8000/api/v1/rag/debug/retrieve \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"query":"你的问题","kb_ids":[1],"top_k":3}' | jq '.data.stages'
```

| `degrade_reason` | 含义 | 排查 |
|---|---|---|
| `rerank_unsupported` | 未配置重排模型，或该模型缺 `rerank_path` | 见下方「重排未生效」 |
| `rerank_timeout` | 重排 RPC 超时（默认 10s，取 `milvus.timeout`） | 上游响应慢或网络抖动 |
| `rerank_failed` | 重排 Provider 报错 | `make rerank-probe` 看真实报错 |
| `rerank_rejected_all` | 重排成功但**全部候选低于阈值** | 阈值过高，见下 |
| （无 degraded） | 重排正常生效 | 用 `make rerank-probe` 核对模型排序是否符合预期 |

**重排未生效（`rerank_unsupported`）**

```bash
# 真实探测重排模型（会打印实际 URL 与分数）
make rerank-probe
```

两个必查项：

1. `llm.models` 里 rerank 模型的 `status` 必须是 `enabled`
2. **必须填 `rerank_path`**（如 `text-rerank/text-rerank`）。

> ★ 第2 条最容易漏。`rerank_path` 是 DashScope 原生路径里的**服务名**，
> 不是模型名 —— 实测拿模型名拼路径，服务端恒返回
> `400 {"code":"InvalidParameter","message":"url error, please check url"}`，
> 而报错完全不提「路径段用错」。留空时本服务直接判定为「不具备重排能力」，
> 不会去拼那个必然失败的 URL。

**全部低于阈值（`rerank_rejected_all`）**

`rerank_score_threshold`（默认 0.3）是**为真实 rerank 模型标定**的。
若换过重排模型，必须重新标定 —— 先用 `make rerank-probe` 看实际分数分布，
再定阈值。参考值（qwen3.7-text-rerank）：强相关 0.998 / 勉强 0.42 / 无关 0.24。

> ⚠️ **不要把这个阈值和 `default_score_threshold` 混用** —— 一个是 rerank
> 相关性分（0–1），一个是向量余弦相似度，量纲不同。

### 7.5 Milvus 相关故障

**症状 A：rag_service 启动时报连不上 Milvus**

| 排查项 | 命令 / 方法 |
|---|---|
| Milvus 是否就绪 | `docker compose exec milvus curl -s http://localhost:9091/healthz` |
| gRPC 端口连通 | `docker compose exec rag_service nc -zv milvus 19530` |
| etcd 是否健康 | `docker compose exec etcd etcdctl endpoint health` |
| MinIO 是否健康 | `curl http://localhost:9000/minio/health/live` |
| 启动顺序 | `docker compose ps` 看 milvus 是否处于 `starting`（首次需 60–90s） |
| 认证配置 | `MILVUS_USER` / `MILVUS_PASSWORD` 是否与 `authorizationEnabled` 匹配 |

```bash
# 查看 Milvus 启动日志（首次启动的初始化信息在这里）
docker compose logs milvus --tail=200 | grep -i "error\|fail\|retry"
```

**症状 B：Milvus 反复重启 / 频繁选举**

| 原因 | 处理 |
|---|---|
| **etcd 磁盘延迟过高** | etcd 对磁盘 fsync 极敏感。要求 IOPS > 500、P99 延迟 < 10ms。**必须用 SSD/NVMe**，网络存储（NFS）基本不可用 |
| 内存不足 | Milvus 索引常驻内存，低于 8 GB 会 OOM。建议 16 GB+ |
| 数据卷丢失 | 确认 PVC / Docker volume 正常挂载，`/var/lib/milvus` 有数据 |

```bash
# 用 fio 测试 etcd 磁盘是否达标（Milvus 官方推荐方法）
mkdir -p /tmp/test-data
fio --rw=write --ioengine=sync --fdatasync=1 --directory=/tmp/test-data \
    --size=2200m --bs=2300 --name=mytest
# 关注 fsync 的 99th percentile 延迟，应 < 10ms
```

**症状 C：检索延迟突然升高**

| 排查项 | 说明 |
|---|---|
| 段（segment）是否过多 | 大量小 segment 会拖慢检索，等待 compaction 完成 |
| `ef` 参数过大 | 默认 64，调大会显著增加延迟 |
| 索引未加载到内存 | 检查 Milvus 内存使用，`queryNode` 缓存是否充足 |
| 是否触发了全表扫描 | 确认检索请求**带了 `kb_id` 过滤**，否则跨库扫描 |
| 写放大异常 | 3.0 下若启用了 Tantivy 类文本索引，构建期磁盘 I/O 较高；3.0.2 已优化写放大 |

**症状 D：3.0 特有 —— 客户端报 proto 类型不匹配 / `undefined` 符号**

| 排查项 | 说明 |
|---|---|
| **SDK 与 proto 版本不一致** | 3.0 服务端要求 `client/v3` + `milvus-proto/go-api/v3`；混入 `client/v2` 会导致**类型不互通**的编译或运行错误 |
| **误用了 eino-ext milvus2 组件** | `eino-ext/components/{indexer,retriever}/milvus2` 依赖 `client/v2`，**不能对接 3.0 服务端**。本项目应在 `pkg/vectordb/milvus3` 内使用自研实现 |
| 依赖树检查 | `go mod graph \| grep milvus-io` 应只出现 `client/v3` 与 `milvus-proto/go-api/v3` |

**症状 E：3.0 特有 —— 认证失败 / 未授权访问告警**

| 排查项 | 说明 |
|---|---|
| `authorizationEnabled` 是否生效 | 3.0 **默认 false**。查 `AUTHORIZATIONENABLED=true` 是否真正注入到容器环境 |
| **默认 root 密码未改** | 3.0 默认 root 密码为 `Milvus`。若审计发现用默认密码登录，立即轮换（见 §8.3） |
| 9091 是否对外 | 见症状 A；3.0 的 compose 还默认暴露 MinIO 9000/9001，需一并检查 |

### 7.6 文档解析失败 / 向量化积压

**症状 A：`documents.status = 3`（解析失败）**

```sql
-- 查最近的失败文档
SELECT doc_id, kb_id, file_name, file_type, error_msg, created_at
FROM documents
WHERE status = 3
ORDER BY created_at DESC LIMIT 20;
```

| 常见原因 | 处理 |
|---|---|
| 文件格式与 `file_type` 不符 | 校验 MIME 与扩展名（已做双重白名单） |
| 加密/受保护的 PDF | 需要用户去除密码后重传；不支持解析加密文档 |
| 扫描件 PDF（无文字层） | 需 OCR 能力，当前版本不支持，应在 UI 提示 |
| 文件过大 | 检查单文件大小限制（建议 ≤ 50MB / 500 页） |
| 解析器 panic | 查看 rag_service 日志，必要时用受限进程隔离 |

**症状 B：`chunk_vec_pending` 指标持续增长（向量化积压）**

```sql
-- 有多少 chunk 卡在「未写入 Milvus」
SELECT count(*) FROM chunks WHERE vec_status <> 1;

-- 按知识库分布
SELECT kb_id, count(*) FROM chunks WHERE vec_status <> 1 GROUP BY kb_id;
```

| 排查项 | 处理 |
|---|---|
| Embedding 接口是否限流 | 查 llm_service 日志中是否有 429 |
| Milvus 写入是否失败 | 查 rag_service 日志中 `milvus insert` 相关错误 |
| 补偿任务是否运行 | `docker compose logs rag_service \| grep -i compensate` |
| 并发是否过大 | 调低 `RAG_INGEST_WORKERS`，避免把 Embedding 配额打满 |

```bash
# 手动触发一次补偿（确认待处理数量后执行）
curl -X POST http://localhost:8885/internal/compensate   # 内网接口，需鉴权
```

**症状 C：检索结果为空或明显不相关**

| 排查项 | 处理 |
|---|---|
| 向量是否真的写入了 | `SELECT count(*) FROM chunks WHERE vec_status = 1 AND kb_id = X;` |
| Milvus 里是否有数据 | 用 Attu 控制台或 `count(*)` 查 Collection |
| `score_threshold` 是否过高 | 默认 0.30；某些 Embedding 模型分数偏低，可下调至 0.2 |
| 维度是否匹配 | `knowledge_bases.embedding_dim` 必须等于 Milvus Collection 的 dim |
| 切片是否过碎 | 检查 `chunk_size`（默认 512 字符），过小会丢失上下文 |
| 是否跨库检索出错 | 确认 `kb_id` 过滤条件正确，且用户有该库权限 |

> ⚠️ **维度不匹配是最隐蔽的错误**：若创建知识库时 `embedding_dim=1024`，但实际 Embedding 模型输出 1536 维，Milvus 写入会直接报错。**排查时首先确认这两个值。**


### 7.7 Sonic 回退 / 编译失败

**症状 A：编译报错 `undefined: GoMapIterator`**

| 原因 | 处理 |
|---|---|
| Sonic 版本 < v1.15.0，不兼容 Go 1.26 的 Swiss Table map 实现 | 升级到 `github.com/bytedance/sonic v1.15.4` |
| 间接依赖锁定了旧版 Sonic | `go mod graph \| grep sonic` 定位上游，用 `replace` 强制统一版本 |

```bash
# 定位是哪个依赖引入了旧版 sonic
go mod graph | grep bytedance/sonic
# 强制统一（在 go.mod 中）
# replace github.com/bytedance/sonic => github.com/bytedance/sonic v1.15.4
go mod tidy && go build ./...
```

**症状 B：启动时打印回退警告（性能退化）**

```
WARNING: sonic only supports (go1.17~1.26 and amd64 CPU) or
(go1.20~1.26 and arm64 CPU), but your environment is not suitable
and will fallback to encoding/json
```

| 原因 | 处理 |
|---|---|
| Go 版本 > 1.26 | 降回 1.26.x（**这是本项目禁止升级 1.27+ 的核心原因**） |
| CPU 架构不支持（如 32 位、部分 ARM 变体） | 换用受支持的 amd64 / arm64 机型 |
| 使用了 `-tags stdjson` 构建标签 | 移除该标签（该标签会强制使用标准库） |
| 使用了 `-tags compat` | 移除；`compat` 模式会走兼容路径，无原生加速 |
| Go 1.24.0 已知问题 | 升级 Go 小版本或加 `-ldflags="-checklinkname=0"` |

**上线前必做校验**

```bash

cat > /tmp/sonic_check.go <<'EOF'
package main

import (
    "fmt"
    "github.com/bytedance/sonic"
)

func main() {
    if sonic.APIKind == sonic.UseSonicJSON {
        fmt.Println("OK: sonic native enabled")

    }
}
EOF
go run /tmp/sonic_check.go

# 2. 确认架构
uname -m    # x86_64 或 arm64

# 3. 确认 Go 版本
go version  # go1.26.x

# 4. 基准对比（可选，验证加速生效）
go test -bench=. -benchmem github.com/bytedance/sonic
```

**其他 Sonic 使用注意事项**

| 项 | 说明 |
|---|---|
| `ConfigFastest` | 跳过输入校验，**仅可用于可信数据源**；处理外部输入必须用 `ConfigDefault` |
| `EscapeHTML` / `SortMapKeys` | 官方标注会**显著拖慢性能**，默认关闭，勿轻易开启 |
| `Pretouch` | 可预编译类型信息，降低首次序列化的 JIT 延迟，适合已知热点类型的服务启动时调用 |
| WebSocket 消息 | Hertz 的 WebSocket 扩展默认也用 Sonic，需同样保证版本 |
| ARM64 | 需 Go 1.20+（本项目 1.26 满足） |

### 7.8 Eino 升级 / 版本问题

**版本策略回顾**（详见 [02-技术架构设计.md §2.2](./02-技术架构设计.md)）

| 线路 | 版本 | 用途 |
|---|---|---|
| 稳定线 | **v0.9.21** | ✅ 生产依赖 |
| alpha 线 | v0.10.0-alpha.x | ⚠️ 仅实验分支，禁止进生产 |

**症状 A：升级 Eino 后编译失败**

Eino 在 0.x 阶段存在 Breaking Changes。v0.9 就曾大规模废弃 API：

| 已废弃 API | 迁移方向 |
|---|---|
| `Agent Transfer` 相关（`SetSubAgents` / `AgentWithOptions` 等） | 改用 `ChatModelAgent + AgentTool` 或 `DeepAgent` |
| `Workflow Agent`（`NewSequentialAgent` / `NewParallelAgent` / `NewLoopAgent`） | 同上 |
| `supervisor.New` / `supervisor.Config` | 同上 |
| `AgentMiddleware` 结构体 + `Middlewares` 字段 | 迁移到接口式 `Handlers []ChatModelAgentMiddleware` |
| `summarization.SummarizeMessages` / `SummarizeOutput` | 改用 `summarization.New` / `TypedMiddleware.Summarize` |

**定位与处理**

```bash
# 1. 确认当前 Eino 版本（防间接依赖拖入 alpha）
go list -m github.com/cloudwego/eino
go list -m github.com/cloudwego/eino-ext/components/model/openai

# 2. 查看依赖图，定位谁引入了 eino
go mod graph | grep cloudwego/eino

# 3. 检查是否混入 alpha 版本
go list -m all | grep -i "eino.*alpha"

# 4. 强制锁定稳定版（go.mod）
# require github.com/cloudwego/eino v0.9.21
# replace  github.com/cloudwego/eino => github.com/cloudwego/eino v0.9.21
go mod tidy && go build ./...

# 5. 编译失败时，对照官方 Migration Notes
#    https://www.cloudwego.io/docs/eino/release_notes_and_migration
```

**症状 B：Adapter 层隔离验证**

```bash
# 确认业务代码未直接依赖 Eino（应只有 provider 层命中）
grep -rn "cloudwego/eino" app/ pkg/ | grep -v "pkg/llm/provider/"
# 期望输出：为空。非空说明隔离被破坏，需修复
```

**升级 Eino 的标准流程**

```
1. 在 feature branch 升级
2. 阅读官方 Migration Notes，逐条比对废弃 API
3. go build ./... 确认编译通过
4. 运行 Provider 契约测试（保证多实现行为一致）
5. 跑端到端回归（同步 + 流式 + 工具调用三条链路）
6. 灰度发布，观察错误率与延迟
7. 合并主干
```

**禁止事项**

| 禁止 | 原因 |
|---|---|
| 生产分支引入 `-alpha` / `-rc` / `-beta` 版本 | 官方明确可能发生 Breaking Changes |
| 直接从 alpha 升级到正式版 | alpha 与正式版不属于同一版本序列，无平滑路径 |
| 业务代码直接 import Eino | 破坏 Adapter 隔离，升级影响面失控 |
| 不锁版本使用 `@latest` | 可能被间接依赖拖入不稳定版本 |

### 8.4 数据备份

```bash
# PostgreSQL 全量备份（逻辑备份，跨版本可恢复）
kubectl -n aegis-infra exec postgres-primary-0 -- \
  pg_dump -U aegis -d aegis -Fc -Z 6 -f /tmp/aegis.dump
kubectl -n aegis-infra cp postgres-primary-0:/tmp/aegis.dump ./aegis-$(date +%F).dump

# 或直接管道导出（更适合小库）
kubectl -n aegis-infra exec postgres-primary-0 -- \
  pg_dump -U aegis -d aegis --no-owner | gzip > aegis-$(date +%F).sql.gz

# 物理备份（大库更快，需 pg_basebackup + WAL 归档）
kubectl -n aegis-infra exec postgres-primary-0 -- \
  pg_basebackup -U replicator -D /backup/base-$(date +%F) -Ft -z -P

# Milvus 数据备份
# 1) etcd 快照（元数据）
kubectl -n aegis-infra exec etcd-0 -- \
  etcdctl snapshot save /tmp/etcd-$(date +%F).db
# 2) MinIO 数据（向量与索引文件）——用 mc mirror 同步到异地
mc mirror --overwrite minio/aegis-milvus /backup/minio/aegis-milvus

# Redis 备份
kubectl -n aegis-infra exec redis-master-0 -- redis-cli BGSAVE
```

> ⚠️ **Milvus 备份必须同时备份 etcd 与 MinIO**：etcd 存 Collection schema 与 segment 元数据，MinIO 存实际向量与索引文件。**只备份其中之一无法恢复**。恢复时需按 etcd → MinIO 的顺序还原。

**备份策略**

| 对象 | 频率 | 保留 | 恢复工具 |
|---|---|---|---|
| PostgreSQL 全量 | 每日 02:00 | 30 天 | `pg_restore` |
| PostgreSQL WAL 归档 | 实时 | 7 天 | PITR（时间点恢复） |
| **Milvus etcd 快照** | 每日 03:00 | 14 天 | `etcdctl snapshot restore` |
| **Milvus MinIO 数据** | 每日 03:30 | 14 天 | `mc mirror`（反向） |
| Redis RDB | 每小时 | 7 天 | 替换 `dump.rdb` |
| Nacos 配置 | 变更时导出 | 全量版本 | 导入 YAML |
| K8s 资源清单 | Git 版本控制 | 永久 | `kubectl apply` |

> **恢复优先级（灾难场景）**：PostgreSQL → Milvus(etcd+MinIO) → Redis → Nacos。因为 PG 是内容真相源，**即使 Milvus 完全丢失，也可从 PG 的 `chunks` 表重新向量化重建**（数据恢复能力是选择"PG 存正文"这一设计的重要回报）。

### 8.5 容量巡检

```bash
# 各服务资源使用
kubectl -n aegis-prod top pods
kubectl -n aegis-infra top pods          # Milvus/etcd/MinIO

# PostgreSQL 表与索引大小
kubectl -n aegis-infra exec postgres-primary-0 -- psql -U aegis -d aegis -c "

       pg_size_pretty(pg_total_relation_size(relid)) AS total,
       pg_size_pretty(pg_relation_size(relid))       AS tbl,
       pg_size_pretty(pg_total_relation_size(relid) - pg_relation_size(relid)) AS idx
FROM pg_statio_user_tables ORDER BY pg_total_relation_size(relid) DESC LIMIT 20;"

# PostgreSQL 死元组（表膨胀预警）
kubectl -n aegis-infra exec postgres-primary-0 -- psql -U aegis -d aegis -c "
SELECT relname, n_live_tup, n_dead_tup,
       ROUND(n_dead_tup*100.0/NULLIF(n_live_tup+n_dead_tup,0),2) AS dead_pct
FROM pg_stat_user_tables WHERE n_dead_tup > 10000 ORDER BY n_dead_tup DESC LIMIT 20;"

# PG 连接数（接近 max_connections 需扩容 PgBouncer 或调参）
kubectl -n aegis-infra exec postgres-primary-0 -- psql -U aegis -c "
```

**容量告警阈值建议**

| 指标 | 告警阈值 | 说明 |
|---|---|---|
| PG 磁盘使用率 | > 80% | 分区表增长快，需提前扩容 |

| `chunks` 表行数 | 按容量规划跟踪 | 对照 §5 容量预估 |

## 9. 应急预案

| 故障场景 | 应急措施 |
|---|---|
| **Nacos 集群不可用** | Kitex 使用本地缓存的服务列表继续工作；紧急修复 Nacos；配置变更暂停 |
| **某模型厂商大面积故障** | 通过 Nacos 将该模型 `status` 置为 `disabled`，流量自动走降级链 |
| **PostgreSQL 主库故障** | 切换从库为主（Patroni/云 RDS 自动切换）；服务开启降级模式（只读 + 缓存兜底） |
| **PostgreSQL 磁盘写满** | 立即 `DETACH` 最旧分区并归档到对象存储；清理 `audit_logs` 旧数据 |
| **Milvus 不可用** | **rag_service 自动降级**：① PG 关键词检索 → ② 空上下文纯 LLM 对话，响应标注 `degraded: true`；**主链路不受影响** |
| **Milvus 索引损坏** | 从 etcd+MinIO 备份恢复；最坏情况：用 PG `chunks` 表**全量重建向量**（代价高但有兜底） |
| **Embedding 接口限流（429）** | 降低 `RAG_INGEST_WORKERS`；暂停解析任务；提高缓存命中率 |
| **Redis 故障** | 会话上下文降级为「无上下文单轮对话」；限流降级为单机限流 |
| **流量突增** | HPA 自动扩容；必要时网关层临时下调单用户限流阈值 |
| **成本异常飙升** | 立即下调全局限流阈值 + 临时禁用高单价模型；**检查是否有大规模重复 Embedding（应被缓存拦截）** |
| **密钥泄露** | 立即轮换 API Key、Milvus 密码、PG 密码，作废旧凭据，审计异常调用记录 |
| **Milvus 9091 意外暴露** | **最高优先级**：立即从网络层切断访问，轮换所有凭据，审计 Milvus 操作日志（存在 CVE-2026-26190 利用风险） |
| **Milvus 升级后需回滚** | **先判断是否已越过四条边界**（Storage V3 写入 / compaction 重写 / 新索引生成 / 新 WAL 语义）。**只要触及任一，镜像回退无效**，必须走备份恢复（etcd + MinIO）。详见 §4.10.1 |
| **Milvus 客户端 proto 不匹配** | 检查依赖树是否混入 `client/v2`；确认 `pkg/vectordb/milvus3` 使用的是 `client/v3` 与 `milvus-proto/go-api/v3` |

**降级开关（Nacos 配置，秒级生效）**

```yaml
degradation:
  disable_streaming: false      # 关闭流式，降为同步
  disable_tools: false          # 关闭工具调用
  disable_context: false        # 关闭多轮上下文（省 token）
  force_model: "deepseek-chat"  # 强制使用低成本模型
  read_only: false              # 只读模式，禁止写操作
  # RAG 相关
  disable_rag: false            # 完全关闭 RAG，所有请求走纯 LLM
  disable_rag_ingest: false     # 暂停文档解析（保留检索能力）
  rag_keyword_fallback: true    # Milvus 不可用时是否降级到 PG 关键词检索
```

> **`disable_rag` vs `disable_rag_ingest` 的区别**：前者影响**读路径**（用户拿不到知识库增强），后者影响**写路径**（新文档不再入库，但已有知识库仍可检索）。Embedding 配额被打满时，优先用 `disable_rag_ingest` 保检索能力。
