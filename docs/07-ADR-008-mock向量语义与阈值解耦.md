# ADR-008 · mock 向量必须具备语义结构，且阈值与生产解耦

| 项目 | 内容 |
|---|---|
| **状态** | ✅ 已采纳 |
| **日期** | 2026-10-08 |
| **相关代码** | `pkg/mockx/mockx.go`、`pkg/conf/conf.go`、`rag_service/internal/retrieve/engine.go` |

---

## 背景

RAG 链路（入库 → 向量化 → 检索 → 引用）必须在 mock 模式下可被冒烟测试验证 —— 这是整个项目「零外部依赖即可验证」的前提。

首版 `mockx.FakeEmbedding` 的实现是**纯随机单位向量**：

```go
h := sha256.Sum256([]byte(seed))   // 文本 → 随机向量
```

当时的想法是「mock 不需要语义，维度对、能跑就行」。

---

## 问题

冒烟测试卡在 `rag.Retrieve`，且**所有环节都报告成功**：

```
[18] rag.UploadDoc   doc_id=3001 切片=2 已向量化=2   ← 入库成功
[20] rag.Retrieve    命中=0 降级=false 耗时=0ms      ← 检索恒为空
```

### 根因

1024 维随机单位向量之间的余弦相似度：

| 性质 | 数值 |
|---|---|
| 期望 | 0 |
| 标准差 | `1/√dim ≈ 0.031` |

而生产检索阈值是 **0.3**（见 [04-数据库设计.md](./04-数据库设计.md) `knowledge_bases.score_threshold`）。

`0.031` 与 `0.3` 相差近 10 倍 —— **mock 模式下向量检索永远不可能命中**，无论文档内容多么相关。

这类缺陷的危险之处在于它不报错：编译通过、入库返回成功、耗时正常、内存向量库没有异常。仅看日志会误判为"检索逻辑有问题"，实际是向量生成侧根本没有语义。

### 排查过程中踩到的其他坑

1. **`sb` nil 解引用**：`retrieve.Engine.Retrieve` 在所有 KB 检索失败时 `sb` 为 nil，Debug 分支直接 `len(sb.ChunkIDs)` 会 panic。
2. **`rec.Chunks` 未回填**：`ingest.Ingest` 把切片交给 `UpdateChunks` 落库，但没有回填 `rec.Chunks`，而 `vectorize` 只读 `rec.Chunks` —— 表现为"入库成功但切片=0"。
3. **变量遮蔽**：`Compensate` 中 `all, _ := ListChunks(...)` 丢弃了 error，随后的 `if err != nil` 检查的是上一轮的 `err`。
4. **Embedding 全缓存命中时 `fill` 传 nil**：`buildEmbedResp` 无条件调用 `fill()` → 空指针 panic。
5. **向量位置错配**：部分缓存命中时，若只按 `pending` 顺序回填而不按原始下标 `idx` 归位，会把 A 文本的向量写进 B 切片 —— 不报错，只静默降低召回。

---

## 决策

### 1. mock 向量改用稀疏词袋投影（hashing trick）

```
分词（ASCII 整词 + 中文 bigram 滑动窗口）
  → sha256 映射到 [0, 256) 一维（带符号，抵消碰撞）
  → 亚线性 TF 加权 (1+log tf)
  → L2 归一化
  → 零填充至目标维度（1024）
```

**关键设计：先哈希到低维（256）再零填充。**

稀疏词袋在 1024 维里只用到几十维，两段文本的共享维度交集极小，相似度被"各占各的维度"稀释。实测把哈希空间降到 256 维后，共享词被显著放大：

| 有效哈希维度 | 强相关 | 长切片 | 无关 |
|---|---|---|---|
| 1024 | 0.258 | 0.242 | 0.000 |
| **256** | **0.388** | **0.113 → 0.24** | 0.000 |

零填充不改变 L2 范数，余弦计算依然正确，且**返回值长度仍为 1024** —— 维度契约不变，Milvus 集合定义无需改动。

分词策略上舍弃了中文单字：单字（"向""量""度"）既冗余又在长文本里高频重复，会同时稀释信号、放大噪声。实测一个 8 token 的查询对 42 token 的切片，共享的 13 个 token 里绝大多数是重复单字。改用 bigram 滑动窗口后信号集中在「向量」「维度」「Milvus」这类高信息量词上。

### 2. mock 阈值与生产阈值解耦

新增配置项 `RAGConf.MockScoreThreshold`（默认 **0.1**），只在 mock 模式生效。

理由是**词袋模型有数学上限**：

```
cos ≈ 共享 token 数 / √(len_q × len_d)
    ≈ 5 / √(8 × 42) ≈ 0.24
```

即便查询与切片共享全部关键词，也突破不了 0.24。若强行套用生产的 0.3，mock 模式下检索将恒为空。

生产阈值 0.3 是为真实 embedding（bge-m3 等）标定的 —— 真实模型能给出 0.7+ 的强相关相似度，两者本就不在同一尺度。**把 mock 阈值与生产阈值解耦，比调参去迁就更符合工程实际。**

### 3. 所有"静默失败"改为显式失败

- `vectorize` 在 `rec.Chunks` 为空时返回带 `doc_id` 的明确错误；
- `buildEmbedResp` 对 `fill == nil` 做防御；
- `Engine.Retrieve` 在 `sb == nil` 时补空结果；
- `mergeEmbeddings` 按原始下标归位，杜绝向量错配。

---

## 后果

### 正面

- mock 模式下 RAG 全链路可被冒烟测试验证，**24 步端到端断言全部通过**；
- 向量语义问题在 `pkg/mockx` 单元测试阶段即被拦截，不必等到链路冒烟；
- 生产阈值语义保持不变，无需为 mock 妥协。

### 负面 / 权衡

- mock 相似度**不代表真实语义质量**。用它做召回率评估会得到乐观或悲观偏差，**RAG 效果必须用真实模型 + 真实语料另行标定**；
- 词袋模型无法表达同义改写（"向量检索" vs "语义搜索"相似度为 0），mock 下测不出这类召回问题；
- 新增一个配置项，需在部署文档中说明其仅 mock 生效。

### 验证方式

```bash
# 单元测试：语义区分度、确定性、归一化、维度契约
go test ./pkg/mockx/ ./pkg/vectordb/mockstore/

# 端到端：24 步断言
scripts/dev.sh up && cd tools/smokeclient && go run .
```
