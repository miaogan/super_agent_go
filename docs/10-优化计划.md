## 一、🔴 P0 — 必须修复

### 1.1 登录接口忽略 BindAndValidate 错误

- **文件**: `gateway/internal/handler/auth.go` L91、L123
- **现状**: `_ = c.BindAndValidate(&req)` 的返回值被丢弃。
- **风险**: 登录/刷新 token 路径上，客户端可构造非法 JSON 绕过字段校验（如 username 为空、password 为空），直接打到下游 auth_service。
- **修复**:
  ```go
  if err := c.BindAndValidate(&req); err != nil {
      handler.ErrBadRequest(c, err)
      return
  }
  ```
  同文件两个位置都要改。

### 1.2 Milvus 字段解析连续忽略 7 个 error

- **文件**: `pkg/vectordb/milvus3/crud.go` L293-L299
- **现状**:
  ```go
  c.Content, _ = strAt(rs, fieldContent, i)
  c.Tenant, _ = strAt(rs, fieldTenant, i)
  c.KBID, _ = intAt(rs, fieldKBID, i)
  c.DocID, _ = intAt(rs, fieldDocID, i)
  c.Seq, _ = int32At(rs, fieldSeq, i)
  c.PageNo, _ = int32At(rs, fieldPageNo, i)
  c.TokenCount, _ = int32At(rs, fieldTokenCount, i)
  ```
- **风险**: Milvus 返回缺失字段/类型不匹配时，`strAt`/`intAt` 返回空值零值并 error，但被忽略。检索结果里的 Chunk 会有 `KbId=0`、`DocId=0`，后续引用溯源全部错乱。
- **修复**: 收集第一个非 nil error，循环结束后检查，出错时返回带 context 的 error 给调用方（检索引擎会据此降级）。

### 1.3 SSE 心跳协程无 panic 恢复

- **文件**: `gateway/internal/sse/sse.go` L109-L124
- **现状**: 心跳 goroutine 里 `w.WriteKeepAlive()` 失败时直接 return，虽然有 `wg.Wait()` 等它，但如果 Hertz Writer 内部 panic（已有 `safeFlush` 注释提到过 nil Writer panic），这个 goroutine 会把整个进程炸掉。
- **修复**: 在心跳 goroutine 入口加 `defer func() { if r := recover(); r != nil { logger.Warn(...) } }()`。

## 二、🟠 P1 — 应该修复

### 2.1 password.Hash 在加密失败时 panic

- **文件**: `pkg/passwd/passwd.go` L43-L46
- **现状**: `rand.Read(salt)` 失败时 `panic(fmt.Sprintf(...))`。
- **风险**: crypto/rand 失败是极端异常（熵源耗尽），但 panic 会让整个进程 crash，包括无辜的 auth_service 和 user_service。应返回 error 让上游处理。
- **建议改法**:
  - `Hash` 签名改为 `func Hash(plain string) (string, error)`
  - 空串返回 `("", nil)`
  - 调用方（user_service 创建用户时）必须处理 error
- **波及**: `user_service/internal/service/user.go`、`auth_service` 中所有 `passwd.Hash` 调用点。

### 2.2 RAG 入库流水线大量忽略状态更新 error

- **文件**: `rag_service/internal/ingest/pipeline.go` L68、L73、L83、L114、L122、L123、L212、L216
- **现状**: `_ = p.meta.UpdateDocStatus(...)` 和 `_ = p.meta.RecountKB(...)` 共 8 处。
- **风险**: 文档入库时 PG 连接抖动 → 状态更新失败 → 文档永远停在 `status=1`（processing），用户永远看不到"处理完成"。补偿任务依赖 `vec_status != 1` 扫描，也捞不到这批卡壳文档。
- **修复**: 不要让它阻断入库，但至少记录 error（含 docID / err），让运维能排查。严重错误（如 PG 挂了）才升级为 return err 让上层感知。

### 2.3 `_ = start` 残留死代码

- **文件**: `agent_service/internal/orchestrate/orchestrate.go` L536
- **现状**: `_ = start`，`start` 在 L404 被赋值为 `time.Now()` 后就再也没用过。推测原本要算 TotalMS，但后来改用 `llmMS`。
- **修复**: 直接删掉 `start := time.Now()` 和 `_ = start`。若确实想记录 total 耗时，在 emit EventDone 时带上。

### 2.4 SSE WriteEvent 返回值被忽略（3 处）

- **文件**: `gateway/internal/sse/sse.go` L84、L161 后的 WriteEvent（L179 里）、L198 Flush
- **现状**:
  - L84 `_ = w.Write(ev)` — retry 事件写入
  - L179 `_ = w.WriteEvent(...)` — `writeJSON` 里
  - L198 `_ = c.Flush()` — safeFlush 里（已有 recover，OK）
- **风险**: L179 的忽略意味着错误事件写入失败时，主循环仍会 break 退出 `writeJSON`，但上层 `Forward` 主循环对这一帧的丢失完全无感知（日志都没有）。
- **修复**: L84 和 L179 至少打一条 Debug 日志。safeFlush 里的忽略没问题（已 recover 且日志）。

### 2.5 SSE Forward 中 `ctx` 丢失请求级上下文

- **文件**: `gateway/internal/sse/sse.go` L59
- **现状**: `ctx := context.Background()`，直接用根 context，丢失了上游带的 TraceID、RequestID、Deadline。
- **修复**: 改成 `ctx := c.Request.Context()` 或 `c.Request.Context().WithCancel(...)`，这样：
  - 链路追踪能串起来
  - 客户端断开时 ctx 自动取消，心跳协程也会退出（虽然已有 streamCtx，但两处独立 cancel 容易不一致）

### 2.6 心跳协程与主循环共用 streamCtx 但 cancel 来源分裂

- **文件**: `gateway/internal/sse/sse.go` L92-L124
- **现状**: `streamCtx, cancel := context.WithTimeout(ctx, timeout)` 用于主循环，心跳协程又自己 select `streamCtx.Done()`。cancel 只在 defer 里调用。
- **问题**: 心跳协程的 ctx 完全依赖 streamCtx，但 `w.WriteKeepAlive()` 返回 error 时协程 return 了，主循环完全不知道，两边各走各的。
- **建议**: 加一个 done channel 或 sync.Once 让任一方退出时通知对方。

### 2.7 llm_service 的 Chat/Rerank 不处理模型降级原因

- **文件**: `llm_service/internal/service/llm.go` L116-L169
- **现状**: 调用 `s.prov.Chat` 失败后只打 warning，降级链由 `pkg/provider/chain` 内部自动重试。但最终失败时只返回 error，不告知上游尝试过哪些 Provider。
- **风险**: agent_service 降级链（模型 fallback）与 llm_service 内部的 Provider 降级链**两层嵌套**，日志里只能看到最外层 error，排查"到底切了几个模型、每个报什么错"很困难。
- **修复**: `provider/chain` 已经有 degrade reason 记录能力，在 llm_service 返回的 ChatResp 里加 degradation 字段（proto 已定义 commonv1.Degradation）。

## 三、🟡 P2 — 建议优化

### 3.1 agent_service ChatStream 函数过长（140+ 行）

- **文件**: `agent_service/internal/orchestrate/orchestrate.go` L397-L538
- **建议拆分**:
  - `readStream(Client) (deltas, reasons, usage, toolcalls, done, error)` — 把流式读取循环抽出来
  - `accumulateMessages(...)` — 把累积逻辑抽出来
  - emit 逻辑保持在主函数（它最依赖 agent 业务语义）
- **收益**: 降低阅读门槛，未来加 tool_call 处理时改动面更小。

### 3.2 retrieve/engine.go 同样过长（766 行）

- **文件**: `rag_service/internal/retrieve/engine.go`
- **建议**: 拆分为：
  - `embedder` — embedding 相关
  - `vectorSearch` — vector + hydrate 阶段
  - `reranker` — rerank 阶段
  - `contextExpander` — expand + title fill
- **但**: 该文件职责边界已清晰（5 个阶段），每个阶段已有独立函数（Retrieve/rerank/buildCandidates/expandContext/keywordFallback），**只是文件行数多**。拆包收益不如加注释高。优先级降低。

### 3.3 user_service repository/memory.go 全量扫描

- **文件**: `user_service/internal/repository/memory.go` L217-L255
- **现状**: ListUsers 先遍历全部用户过滤，再排序，再分页。O(N)。
- **风险**: mock 模式没问题，但如果有朝一日换 PG 实现，当前接口签名 `(filter, page, size)` 没暴露任何数据库友好的查询语义，换 PG 时只能在实现层偷偷加索引而接口层看不出来。
- **建议**: 加 TODO 注释标注"mock-only，生产实现需 DB 索引"，或把 repository 接口里加注释说明查询复杂度预期。

### 3.4 agent_service store.go 单 mutex 保护全部 map

- **文件**: `agent_service/internal/store/store.go`
- **现状**: session 和 message map 共用一个 `sync.Mutex`，`RLock` 读、`Lock` 写。会话和消息并发量不同，session CRUD 远少于 message append。
- **建议**: 拆两把锁（sessionMu / messageMu）。当前数据量不大不急，但文档里标清楚。

### 3.5 环境变量 applyEnv 是手工映射

- **文件**: `pkg/conf/conf.go` L496-L697
- **现状**: 每个 `AEGIS_*` 环境变量都手工写一行 apply 语句。
- **问题**: 新增配置字段时很容易忘加 env 覆盖 —— 所以项目有 `make env-audit` 来兜底。
- **替代方案**: 用 struct tag 反射自动生成 env key（如 `env:"llm.models[0].api_key"`），减少手写映射的行数和出错面。但反射有性能损耗且模型列表索引是动态的，改造量不小。
- **建议**: 保持现状，CI 门禁已经兜底。在 applyEnv 函数顶部加注释说明这是刻意手工映射而非遗漏。

### 3.6 Milvus 向量库 Mock 阈值与生产解耦（已做但可更清晰）

- **文件**: `rag_service/internal/retrieve/engine.go` L329-L340
- **现状**: mock 阈值下调逻辑在 `rerankThreshold()` 和 `scoreThreshold()` 里各一份。
- **建议**: 提炼成一个小函数 `effectiveThreshold(mockMode, prod, mockDefault) float64`，让阈值计算更集中。

### 3.7 pkg/provider/chain 降级链与 llm_service 冗余包装

- **文件**: `pkg/provider/chain/chain.go` + `llm_service/internal/providerfactory/factory.go`
- **现状**: chain.go 有 385 行，实现了熔断、候选选择、错误分类。factory.go 只有 20 行左右，只是调 `chain.New`。
- **建议**: factory.go 里可以把 chain 创建时的 Options 来源（熔断阈值、候选选择策略）也注入，让 chain 行为可配置。当前 chain 内部有硬编码的熔断参数（查一下 chain.go L70-90）。

### 3.8 Compensator 没有并发控制

- **文件**: `rag_service/internal/ingest/pipeline.go` L485-L501
- **现状**: `go func() { for select { Compensate(batch) } }()`，每次 ticker 触发直接 `Compensate(ctx, batch)`。
- **风险**: 如果 `Compensate` 比 ticker interval 慢，上一个还没跑完下一个又来了（虽然 ctx.Done 能退出，但中间过程没有并发限制）。
- **建议**: 加一个 `sync.Mutex` 或用 `singleflight.Group` 保证同一时间只有一个补偿实例在跑。

## 七、架构观察（不改但值得注意）

1. **两层降级链嵌套**: `agent_service → llm_service → provider/chain`，每层都有降级逻辑。当前行为正确但日志分散，排查时需要跨三层对照。建议在每条链上加统一的 degradation 字段透传。

2. **provider/chain 的熔断是内存级**: 进程重启后熔断状态丢失。如果未来有需要可以迁到 Redis。当前单机部署场景下够用。

3. **Compensator 是唯一的异步写入**: 没有任务队列（Celery / asynq），直接 `go func() { for select }`。单实例场景没问题，多实例部署时多个补偿器会抢同一批 vec_status != 1 的切片。建议后续加 Redis 分布式锁。

4. **用户服务内存存储**: 单机 mock 模式够用。生产环境换 DB 是必做事项，repository 接口签名已预留空间。
