## 1. 设计原则

| 原则 | 说明 |
|---|---|
| **主键策略** | 业务表用 `BIGINT` 雪花 ID（`BIGINT` 非 `UNSIGNED`，PG 无无符号整型）；对外暴露的 ID 使用字符串前缀（如 `sess_` `agent_`） |
| **自增主键** | 纯关联表/日志表用 `BIGINT GENERATED ALWAYS AS IDENTITY`（PG 标准写法，替代 MySQL `AUTO_INCREMENT`） |
| **软删除** | 用户、会话、Agent 使用 `deleted_at` 软删除，避免误删 |
| **时间字段** | 统一 `created_at` / `updated_at` / `deleted_at`，类型 **`TIMESTAMPTZ`**（带时区，微秒精度，天然支持多时区） |
| **`updated_at` 维护** | PG 无 `ON UPDATE CURRENT_TIMESTAMP`，统一由**触发器** `set_updated_at()` 维护（见 §7.1） |
| **布尔与状态** | 布尔语义字段用 `BOOLEAN`；多值状态字段用 `SMALLINT`（替代 `TINYINT`） |
| **JSON 字段** | 统一 **`JSONB`**（二进制存储，支持 GIN 索引与 `->` `@>` 操作符，性能显著优于 `JSON`） |
| **字符类型** | PG 的 `VARCHAR(n)` 与 `TEXT` 性能无差异，短字段保留 `VARCHAR(n)` 起约束作用，长文本直接用 `TEXT` |
| **字符集** | 库级 UTF8，支持 emoji（AI 对话中常见） |
| **分表规划** | `messages`、`token_usage` 数据量大，使用**原生声明式分区**（PG 原生分区能力优于 MySQL） |
| **索引** | 高频查询字段建索引；避免过度索引影响写入 |
| **金额** | 成本用 `DECIMAL(16,6)`，禁止用 FLOAT/DOUBLE |
| **命名** | 全小写下划线；索引 `idx_`、唯一约束 `uk_`、外键 `fk_`、触发器 `trg_` |

### 1.1 MySQL → PostgreSQL 语法映射（迁移速查）

| MySQL | PostgreSQL 18 | 备注 |
|---|---|---|
| `BIGINT UNSIGNED` | `BIGINT` | PG 无无符号类型；雪花 ID 最高位为 0，`BIGINT` 足够 |
| `INT UNSIGNED AUTO_INCREMENT` | `INTEGER GENERATED ALWAYS AS IDENTITY` | 或 `BIGSERIAL`（等价，但 IDENTITY 是 SQL 标准） |
| `TINYINT` | `SMALLINT` | 状态位可用 `BOOLEAN` |
| `DATETIME(3)` | `TIMESTAMPTZ` | PG 微秒精度，无需指定精度；带时区更安全 |
| `DATE` | `DATE` | 一致 |
| `JSON` | `JSONB` | **强烈建议**，可建 GIN 索引 |
| `MEDIUMTEXT` / `LONGTEXT` | `TEXT` | PG 的 `TEXT` 无长度上限 |
| `CHAR(64)` | `CHAR(64)` | 一致（定长，哈希用） |
| `DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3)` | 建 `trg_set_updated_at` 触发器 | **无直接等价物**，必须用触发器 |
| `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4` | 移除 | PG 单引擎，字符集在库级/实例级指定 |
| `COMMENT '...'` | `COMMENT ON COLUMN ... IS '...'` | 需独立语句，建议统一放 `COMMENT ON` 块 |
| `utf8mb4_0900_ai_ci` | `und-x-icu`（或 `zh-x-icu`） | ICU 排序规则，支持中文 |
| `KEY idx_x (a, b)` | 独立 `CREATE INDEX idx_x ON t (a, b);` | PG 索引与建表语句分离 |
| `UNIQUE KEY uk_x (a)` | `CONSTRAINT uk_x UNIQUE (a)` | 建表内联即可 |
| 分区 `PARTITION BY RANGE` | `PARTITION BY RANGE`（声明式） | PG 分区为表级语法，需父表 + 子分区 |
| `AUTO_INCREMENT` 重置 | `ALTER TABLE t ALTER COLUMN id RESTART WITH n` | IDENTITY 列专用语法 |

## 3. 表结构定义

> 所有语句均为 PostgreSQL 18 语法。`COMMENT ON` 语句统一集中在 §7.4，避免正文过长。

### 3.1 `users` — 用户表

```sql
CREATE TABLE users (
  uid             BIGINT       PRIMARY KEY,
  username        VARCHAR(32)  NOT NULL,
  password_hash   VARCHAR(128) NOT NULL,
  nickname        VARCHAR(64)  NOT NULL DEFAULT '',
  avatar          VARCHAR(512) NOT NULL DEFAULT '',
  email           VARCHAR(128) NOT NULL DEFAULT '',
  phone           VARCHAR(32)  NOT NULL DEFAULT '',
  status          SMALLINT     NOT NULL DEFAULT 1,
  dept_id         BIGINT       NOT NULL DEFAULT 0,
  last_login_at   TIMESTAMPTZ,
  last_login_ip   VARCHAR(64)  NOT NULL DEFAULT '',
  created_at      TIMESTAMPTZ  NOT NULL DEFAULT now(),
  updated_at      TIMESTAMPTZ  NOT NULL DEFAULT now(),
  deleted_at      TIMESTAMPTZ,
  CONSTRAINT uk_users_username UNIQUE (username),
  CONSTRAINT uk_users_email    UNIQUE (email)
);

CREATE INDEX idx_users_phone      ON users (phone);
CREATE INDEX idx_users_dept       ON users (dept_id);
CREATE INDEX idx_users_created    ON users (created_at);
-- 软删除查询优化：仅索引未删除行
CREATE INDEX idx_users_alive      ON users (uid) WHERE deleted_at IS NULL;
```

| 字段 | 类型 | 说明 |
|---|---|---|
| uid | BIGINT | 主键，雪花 ID |
| username | VARCHAR(32) | 唯一，4–32 位 |
| password_hash | VARCHAR(128) | BCrypt，不可逆 |
| status | SMALLINT | 1 启用 / 2 禁用 / 3 锁定 |
| deleted_at | TIMESTAMPTZ | 软删除，非 NULL 表示已删除 |

> **PG 特色**：`idx_users_alive` 是**部分索引**（Partial Index），只为未删除行建索引。相比 MySQL 全量索引，占用显著更小、查询更快。这是软删除场景下的推荐做法。

### 3.7 `agents` — 智能体表

```sql
CREATE TABLE agents (
  agent_id       VARCHAR(64)  PRIMARY KEY,
  uid            BIGINT       NOT NULL,
  name           VARCHAR(128) NOT NULL,
  description    VARCHAR(512) NOT NULL DEFAULT '',
  system_prompt  TEXT         NOT NULL,
  model          VARCHAR(64)  NOT NULL DEFAULT '',
  temperature    NUMERIC(3,2) NOT NULL DEFAULT 0.70,
  max_tokens     INTEGER      NOT NULL DEFAULT 4096,
  context_rounds INTEGER      NOT NULL DEFAULT 20,
  status         SMALLINT     NOT NULL DEFAULT 1,
  is_public      BOOLEAN      NOT NULL DEFAULT FALSE,
  -- RAG 关联：Agent 可挂载若干知识库（数组，PG 原生支持）
  kb_ids         BIGINT[]     NOT NULL DEFAULT '{}',
  created_at     TIMESTAMPTZ  NOT NULL DEFAULT now(),
  updated_at     TIMESTAMPTZ  NOT NULL DEFAULT now(),
  deleted_at     TIMESTAMPTZ
);

CREATE INDEX idx_agents_uid    ON agents (uid);
CREATE INDEX idx_agents_status ON agents (status);
CREATE INDEX idx_agents_public ON agents (is_public, status);
-- GIN 索引支持 kb_ids 反向查询「哪些 Agent 用了知识库 X」
CREATE INDEX idx_agents_kb_ids ON agents USING GIN (kb_ids);
```

| 字段 | 类型 | 说明 |
|---|---|---|
| agent_id | VARCHAR(64) | 主键，`agent_xxx` |
| temperature | NUMERIC(3,2) | 温度 0–2（`DECIMAL` 的 PG 标准写法） |
| status | SMALLINT | 1 草稿 / 2 已发布 / 3 下线 |
| **kb_ids** | **BIGINT[]** | **本次新增**：挂载的知识库 ID 数组 |

> **PG 特色**：`BIGINT[]` **原生数组类型** + **GIN 索引**，直接表达「Agent 挂载多个知识库」，无需中间表。MySQL 需额外建 `agent_knowledge_bases` 关联表，PG 用数组更简洁，且支持 `kb_ids @> ARRAY[5]` 这类包含查询。


### 3.10 `messages` — 消息表（分区表）

本项目 `messages` 年增量约 7300 万行，使用 **PostgreSQL 声明式分区**（`PARTITION BY RANGE`）。

```sql
-- 父表（逻辑表，本身不存数据）
CREATE TABLE messages (
  msg_id              VARCHAR(64) NOT NULL,
  session_id          VARCHAR(64) NOT NULL,
  uid                 BIGINT      NOT NULL,
  role                VARCHAR(16) NOT NULL,
  content             TEXT        NOT NULL,
  tool_calls          JSONB,
  tool_call_id        VARCHAR(64) NOT NULL DEFAULT '',
  model               VARCHAR(64) NOT NULL DEFAULT '',
  prompt_tokens       INTEGER     NOT NULL DEFAULT 0,
  completion_tokens   INTEGER     NOT NULL DEFAULT 0,
  finish_reason       VARCHAR(32) NOT NULL DEFAULT '',
  latency_ms          INTEGER     NOT NULL DEFAULT 0,
  -- RAG 溯源：本条回答引用了哪些 chunk
  cited_chunk_ids     VARCHAR(64)[] NOT NULL DEFAULT '{}',
  created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (msg_id, created_at)          -- ★ 分区键必须包含在主键内
) PARTITION BY RANGE (created_at);

-- 按月创建子分区（示例：2026 年 Q4）
CREATE TABLE messages_2026_10 PARTITION OF messages
  FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
CREATE TABLE messages_2026_11 PARTITION OF messages
  FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');
CREATE TABLE messages_2026_12 PARTITION OF messages
  FOR VALUES FROM ('2026-12-01') TO ('2027-01-01');

-- 子分区各自建索引（PG 会自动为后续 ATTACH 的分区建立）
CREATE INDEX idx_messages_session_time ON messages (session_id, created_at DESC);
CREATE INDEX idx_messages_uid_time     ON messages (uid, created_at DESC);
```

> ⚠️ **分区表的关键约束**：PostgreSQL 要求**分区键必须包含在所有主键/唯一约束中**，因此主键定义为 `(msg_id, created_at)` 而非单独的 `msg_id`。这是从 MySQL 迁过来最容易踩的坑。
>
> ✅ **PG 的替代方案（推荐）**：使用 **`PARTITION BY RANGE (created_at)` + 应用层自动建分区**，或引入 `pg_partman` 扩展自动滚动分区。运维上比 MySQL 的手工分区维护更省心。
>
> **`cited_chunk_ids`**：本次新增，记录回答引用的 RAG chunk，用于前端「查看引用来源」与溯源审计。

### 3.14 `prompt_templates` — Prompt 模板表


### 4.1 Key 规范

| Key 模式 | 类型 | TTL | 用途 |
|---|---|---|---|
| `aegis:session:{session_id}:ctx` | List | 24h | 会话上下文消息（JSON 字符串） |
| `aegis:session:{session_id}:meta` | Hash | 24h | 会话元信息（已用 token 数、摘要） |

| `aegis:token:refresh:{uid}:{device}` | String | 7d | Refresh Token |
| `aegis:quota:{subject}` | Hash | — | 配额已用量（`used` 字段） |
| `aegis:cb:{model}:fail` | String | 10s | 熔断失败计数 |
| `aegis:cb:{model}:open` | String | 30s | 熔断开关标记 |
| `aegis:rate:{dim}:{id}:{path}` | String | 1s | 限流计数器 |
| `aegis:lock:quota:{subject}` | String | 5s | 配额扣减分布式锁 |
| `aegis:cache:user:{uid}` | Hash | 5m | 用户信息缓存 |
| `aegis:cache:agent:{agent_id}` | Hash | 5m | Agent 配置缓存 |
| **`aegis:rag:embed:{sha256}`** | **String** | **24h** | **Embedding 结果缓存（相同文本不重复调模型）** |
| **`aegis:rag:search:{kb}:{hash}`** | **String** | **5m** | **检索结果缓存（同 query 命中）** |
| **`aegis:rag:task:{doc_id}`** | **Hash** | **2h** | **文档解析/向量化任务进度** |

### 4.2 会话上下文结构

```
Key: aegis:session:sess_abc123:ctx
Type: List

[0] {"role":"user","content":"你好","ts":1759945210000}
[1] {"role":"assistant","content":"你好！...","ts":1759945212000}
[2] {"role":"user","content":"帮我...","ts":1759945300000}
...
```

**操作**

| 操作 | 命令 |
|---|---|
| 追加消息 | `RPUSH` |
| 读取最近 N 条 | `LRANGE key -N -1` |
| 截断（滑动窗口） | `LTRIM key -N -1` |
| 设置过期 | `EXPIRE key 86400` |

### 4.3 限流实现（固定窗口）

```lua
-- 固定窗口计数（简单高效）
local key = KEYS[1]
local limit = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local current = redis.call('INCR', key)
if current == 1 then
  redis.call('EXPIRE', key, window)
end
if current > limit then
  return 0   -- 超限
end
return 1     -- 放行
```

### 4.4 熔断计数

```
调用失败 → INCR aegis:cb:{model}:fail; EXPIRE 10s
        → 若 >= threshold（如 20）
        → SET aegis:cb:{model}:open 1 EX 30   （熔断 30s）
调用前先 GET aegis:cb:{model}:open，命中则直接降级
```

## 5. 数据量预估与容量规划

| 表 | 单条大小 | 日增量 | 年增量 | 策略 |
|---|---|---|---|---|
| users | ~500 B | 100 | 3.6 万 | 单表 |
| sessions | ~400 B | 5,000 | 180 万 | 按 uid 哈希分片（中间件）或原生分区 |
| **messages** | ~2 KB | 100,000 | **7,300 万** | 原生月度分区 |
| **token_usage** | ~300 B | 100,000 | **3,650 万** | 原生月度分区 + 日聚合 |
| audit_logs | ~500 B | 200,000 | 7,300 万 | 原生月度分区，90 天归档 |
| **knowledge_bases** | ~300 B | 10 | 3,650 | 单表 |
| **documents** | ~1 KB | 500 | 18 万 | 单表 |
| **chunks** | ~1 KB | 50,000 | **1,825 万** | 按 `kb_id` 哈希分片；向量在 Milvus |

**容量建议**

**PostgreSQL 侧**

- `messages` 是最大表，必须分区；建议按 `created_at` 月度分区，历史冷数据用 `DETACH PARTITION` 归档到对象存储
- `token_usage` 保留明细 6 个月，聚合表长期保留
- 读写分离：报表类查询走只读从库（PG 流复制 + 应用侧 `target_session_attrs=read-write`/`any` 路由）
- **连接池必配**：PG 为进程模型，每连接约 5–10 MB 内存。必须经 **PgBouncer**（transaction 模式）复用连接，否则高并发下连接数会先于 CPU 成为瓶颈

**Milvus 侧**（1024 维 / float32）

| 项 | 计算 | 结果 |
|---|---|---|
| 单向量 | 1024 × 4 B | 4 KB |
| 1800 万 chunk 原始向量 | 1800万 × 4 KB | **约 72 GB** |
| HNSW 索引开销 | 约原始数据的 1.2–1.5 倍 | **约 90–110 GB** |
| 热数据内存建议 | 索引 + 查询缓存 | **建议 64 GB 起** |

> 若存储紧张，可用 Milvus 的 **`FLOAT16` / `BFLOAT16` 向量类型**或 **量化（IVF_SQ8、SCANN）** 将向量体积压缩 50–75%。本项目 M1–M3 阶段数据量远低于此，可按需再优化。

## 7. PostgreSQL 运维要点

### 7.1 `updated_at` 自动维护触发器

PostgreSQL **没有** MySQL 的 `ON UPDATE CURRENT_TIMESTAMP`，必须用触发器。统一方案如下：

```sql
-- 通用触发器函数（只建一次）
CREATE OR REPLACE FUNCTION set_updated_at()
RETURNS TRIGGER AS $$
BEGIN
  NEW.updated_at := now();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- 为每张含 updated_at 的表挂载
CREATE TRIGGER trg_users_updated_at
  BEFORE UPDATE ON users
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();

CREATE TRIGGER trg_roles_updated_at
  BEFORE UPDATE ON roles
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();

CREATE TRIGGER trg_departments_updated_at
  BEFORE UPDATE ON departments
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();

CREATE TRIGGER trg_agents_updated_at
  BEFORE UPDATE ON agents
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();

CREATE TRIGGER trg_tools_updated_at
  BEFORE UPDATE ON tools
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();

CREATE TRIGGER trg_sessions_updated_at
  BEFORE UPDATE ON sessions
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();

CREATE TRIGGER trg_quotas_updated_at
  BEFORE UPDATE ON quotas
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();

CREATE TRIGGER trg_prompt_templates_updated_at
  BEFORE UPDATE ON prompt_templates
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();

-- RAG 域
CREATE TRIGGER trg_knowledge_bases_updated_at
  BEFORE UPDATE ON knowledge_bases
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();

CREATE TRIGGER trg_documents_updated_at
  BEFORE UPDATE ON documents
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();
```

> ⚠️ **重要提醒**：触发器维护 `updated_at` 意味着**批量 UPDATE 也会逐行触发**。大批量数据修正时应临时禁用触发器：
> ```sql
> ALTER TABLE messages DISABLE TRIGGER trg_messages_updated_at;
> -- ... 批量更新 ...
> ALTER TABLE messages ENABLE TRIGGER trg_messages_updated_at;
> ```

### 7.2 关键参数建议

| 参数 | 默认值 | 建议值 | 说明 |
|---|---|---|---|

### 7.3 慢查询与健康检查

```sql
-- 当前运行中超过 5 秒的查询
SELECT pid, now() - query_start AS duration, state, query
FROM pg_stat_activity
WHERE state <> 'idle' AND now() - query_start > interval '5 seconds'
ORDER BY duration DESC;

-- 表膨胀与 vacuum 状态
SELECT relname, n_live_tup, n_dead_tup,
       ROUND(n_dead_tup * 100.0 / NULLIF(n_live_tup + n_dead_tup, 0), 2) AS dead_pct,
       last_autovacuum, last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC LIMIT 20;

-- 索引使用率（找出未使用索引，考虑删除）
SELECT relname, indexrelname, idx_scan
FROM pg_stat_user_indexes
WHERE idx_scan = 0 AND indexrelname NOT LIKE '%_pkey'
ORDER BY pg_relation_size(indexrelid) DESC;

-- 表大小 TOP 20
SELECT relname,
       pg_size_pretty(pg_total_relation_size(relid)) AS total_size,
       pg_size_pretty(pg_relation_size(relid))       AS table_size,
       pg_size_pretty(pg_total_relation_size(relid) - pg_relation_size(relid)) AS index_size
FROM pg_catalog.pg_statio_user_tables
ORDER BY pg_total_relation_size(relid) DESC LIMIT 20;
```

> **PG 与 MySQL 的关键运维差异**：PG 采用 **MVCC + 多版本行存储**，UPDATE 产生新行版本（旧行成为 dead tuple），依赖 **autovacuum** 回收。因此必须监控 `n_dead_tup`，并针对高频更新的表（如 `sessions`、`quotas`）**单独调优 autovacuum 触发阈值**，否则会出现表膨胀。

## 8. RAG 数据设计

### 8.1 数据分治原则

RAG 场景的数据天然分两类，分而治之：

| 数据 | 存放位置 | 理由 |
|---|---|---|
| 知识库元信息、文档记录、解析状态 | **PostgreSQL** | 强事务、关系约束、状态机、报表 |
| **Chunk 正文文本** | **PostgreSQL**（`chunks.content`） | 需要全文检索、需要与元数据 JOIN 取回原文 |
| **Chunk 向量** | **Milvus** | 高维 ANN 检索，PG 无原生向量索引 |
| 检索必需标量（`kb_id`、`doc_id`、`chunk_id`） | **Milvus**（标量字段，冗余一份） | 支持 Milvus 侧**标量过滤 + 向量检索**一次完成，减少回表 |

> **设计取舍**：chunk 正文**不存 Milvus**，只存 PG。Milvus 检索返回 `chunk_id` 列表后回 PG 取正文。这样 PG 是唯一的**内容真相源（Source of Truth）**，Milvus 即使重建索引也不会丢数据。

### 8.2 `knowledge_bases` — 知识库表

```sql
  -- 统计

  -- 状态
```

```sql
CREATE INDEX idx_documents_uid       ON documents (uid);
CREATE INDEX idx_documents_file_hash ON documents (kb_id, file_hash);  -- 同库去重
CREATE INDEX idx_documents_metadata  ON documents USING GIN (metadata jsonb_path_ops);
```

| status | 含义 |
|---|---|
| 0 | 待处理（已上传，未开始解析） |
| 1 | 解析/切片中 |
| 2 | 已完成（向量已入库） |
| 3 | 失败（见 `error_msg`） |

> `file_hash` + `(kb_id, file_hash)` 索引用于**上传去重**：同一知识库内重复文件直接复用已有 chunk，省一次 Embedding 成本。

### 8.4 `chunks` — 文档切片表

```sql
CREATE TABLE chunks (
  chunk_id     VARCHAR(64) PRIMARY KEY,     -- chk_xxx，全局唯一
  doc_id       BIGINT      NOT NULL,
  kb_id        BIGINT      NOT NULL,
  seq          INTEGER     NOT NULL,        -- 在文档内的顺序号
  content      TEXT        NOT NULL,        -- 切片正文（内容真相源）
  token_count  INTEGER     NOT NULL DEFAULT 0,
  char_count   INTEGER     NOT NULL DEFAULT 0,
  -- 定位信息：支持「跳转到原文位置」
  start_offset INTEGER     NOT NULL DEFAULT 0,
  end_offset   INTEGER     NOT NULL DEFAULT 0,
  page_no      INTEGER     NOT NULL DEFAULT 0,
  heading      VARCHAR(512) NOT NULL DEFAULT '',
  -- Milvus 关联
  milvus_pk    BIGINT      NOT NULL DEFAULT 0,
  vec_status   SMALLINT    NOT NULL DEFAULT 0,   -- 0待写 1已写 2失败
  metadata     JSONB,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_chunks_doc    ON chunks (doc_id, seq);
CREATE INDEX idx_chunks_kb     ON chunks (kb_id);
CREATE INDEX idx_chunks_milvus_pk ON chunks (milvus_pk);
CREATE INDEX idx_chunks_vec_status ON chunks (vec_status) WHERE vec_status <> 1;

-- 全文检索：中文需 zhparser/pg_jieba 扩展，或先用 pg_trgm 模糊匹配
CREATE INDEX idx_chunks_content_trgm ON chunks USING GIN (content gin_trgm_ops);
```

> **`vec_status` 与 `milvus_pk` 是"双写一致性"的关键**：PG 与 Milvus 无分布式事务，采用 **「先写 PG（`vec_status=0`）→ 写 Milvus 拿到 pk → 回填 `milvus_pk` 与 `vec_status=1`」** 的最终一致方案。`idx_chunks_vec_status` 为部分索引，专门用于**补偿任务扫描未完成的 chunk**。

### 8.5 Milvus Collection 设计

> **版本基线**：Milvus **3.0.2**，Go 客户端 `github.com/milvus-io/milvus/client/v3 v3.0.2`，proto 为 `milvus-proto/go-api/v3`。适配代码位于 `pkg/vectordb/milvus3`（自研，实现 Eino 的 `Indexer`/`Retriever` 接口），**不直接使用 eino-ext 的 `milvus2` 组件**（依赖 `client/v2`，与 3.0 类型不互通）。详见 [02-技术架构设计.md § 4.8.1.1](./02-技术架构设计.md)。

```yaml
collection_name: aegis_chunks
description: "Aegis 知识库切片向量"
# 向量维度与 knowledge_bases.embedding_dim 严格一致
dimension: 1024
metric_type: COSINE           # 归一化后余弦等价于点积；中文 RAG 常用
index_type: HNSW              # ★ 3.0 下继续使用传统 HNSW，不启用 SINDI 等新算法
index_params:
  M: 16                       # 图连接数，越大召回越高、内存越大
  efConstruction: 200         # 建索引候选数，越大索引质量越高、建得越慢
search_params:
  ef: 64                      # 查询候选数，越大召回越高、越慢
```

> ⚠️ **索引版本约束（回滚保障）**：3.0 的新索引格式（`targetVecIndexVersion` 提升到 10 / `targetScalarIndexVersion` 提升到 4）是 **opt-in** 的。本项目**保持默认值不提升**，使用传统 HNSW。理由：新索引文件格式旧版本无法读取，会关闭回滚窗口。详见 [05-部署运维手册 § 4.10.1](./05-部署运维手册.md)。

**Schema（字段定义）**

| 字段名 | 类型 | 说明 |
|---|---|---|
| `pk` | `Int64`（主键，auto_id） | Milvus 内部主键，回填到 `chunks.milvus_pk` |
| `chunk_id` | `VarChar(64)` | 业务 chunk ID，与 PG 关联 |
| `kb_id` | `Int64` | 知识库 ID，**标量过滤字段** |
| `doc_id` | `Int64` | 文档 ID，**标量过滤字段** |
| `seq` | `Int32` | 文档内顺序，用于命中外扩上下文 |
| `vector` | `FloatVector(1024)` | 向量本体 |

**分区策略**

```python
# 按 kb_id 做分区键，检索时指定 partition，天然隔离不同知识库
collection.create_partition("kb_1001")
```

> 当知识库数量多、单个知识库体量大时，**使用 `partition_key_field = "kb_id"`**（Milvus 2.4 引入，3.0 继续支持），可按知识库物理隔离数据，检索性能显著提升且避免跨库污染。
>
> **本项目策略（M1–M5）**：优先用 `kb_id` 标量字段 + 过滤表达式实现隔离。原因：① 过滤表达式的组合更灵活（可同时按 `doc_id` 排除）；② 便于后续演进为多租户隔离。当单 Collection 数据量超过千万级、且跨库检索占比升高时，再切换到 `partition_key_field`。

**检索请求示例（标量过滤 + 向量检索一次完成）**

```python
res = client.search(
    collection_name="aegis_chunks",
    data=[query_vector],
    limit=5,
    filter='kb_id in [1001, 1002] and doc_id != 88',   # 标量过滤下推到 Milvus
    output_fields=["chunk_id", "doc_id", "seq"],
    search_params={"metric_type": "COSINE", "params": {"ef": 64}},
)
# 拿到 chunk_id 列表 → 回 PostgreSQL 取 content（内容真相源）
```

**Go 侧对应写法（`pkg/vectordb/milvus3`，示意）**

```go
// client/v3 的调用形态与 v2 不同：接口由 milvusclient.Client 提供
res, err := s.cli.Search(ctx, milvusclient.NewSearchOption(s.coll, topK, [][]float32{qvec}).
    WithFilter(`kb_id in [1001, 1002]`).
    WithOutputFields("chunk_id", "doc_id", "seq").
    WithSearchParam("ef", "64"))   // ★ 参数以字符串传入
```

> ⚠️ **维度一致性是硬约束**：`dim` 来自 Embedding 模型（bge-m3 为 **1024**），**建库后不可修改**。更换 Embedding 模型 = 新建 Collection + 全量重建向量。`knowledge_bases.embedding_dim` 与 `chunks.embed_model` 用于上线前校验，维度不匹配时应**拒绝写入并告警**，绝不能静默截断或补零。

### 8.6 一致性保障：补偿任务

PG 与 Milvus 双写采用**最终一致**，需一个补偿任务兜底：

```sql
-- 找出「PG 有、Milvus 未确认」的 chunk，重新向量化
SELECT chunk_id, kb_id, doc_id, content
FROM chunks
WHERE vec_status <> 1
  AND created_at < now() - interval '10 minutes'   -- 给正常流程留出窗口
ORDER BY created_at
LIMIT 1000;
```

> 补偿任务由 `rag_service` 内置的定时 Job 执行（每 5 分钟一次）。删除场景同理：**先软删 PG（记录待删的 `milvus_pk`）→ 异步删 Milvus**，确保不会出现"Milvus 有向量但 PG 无正文"的悬挂数据。
>
> **Milvus 侧的删除语义**：`client/v3` 的 `Delete` 是**标记删除**，物理清除依赖后续 compaction。因此补偿任务在删除时需关注 `pk` 复用风险——本方案主键为 `auto_id` 自增，不会复用，可安全依赖软删 + 异步物理删除。
>
> **与 3.0 新特性的关系**：3.0 提供 **Entity TTL**（按行过期）可用于"文档过期自动清理"场景，但本项目**暂不启用**——它属于影响数据状态的功能，启用前需评估回滚边界（见 [05-部署运维手册 § 4.10.1](./05-部署运维手册.md)）。当前仍以 `vec_status` 状态机 + 定时补偿作为一致性保障。
